## 🔴 Critical

### CR-1 · `migrateTasksV2` silently nulls every session→task link on legacy DBs
[`src/core/db.ts:243`](src/core/db.ts) (the `DROP TABLE tasks` at ~`:269`), invoked from [`getDb()`](src/core/db.ts) and [`db-pool.ts:51`](src/core/db-pool.ts).

`PRAGMA foreign_keys = ON` is set *before* migration runs. `sessions.task_id` is declared `REFERENCES tasks(id) ON DELETE SET NULL` ([`db-schema.ts:44`](src/core/db-schema.ts)). In SQLite, `DROP TABLE tasks` performs an implicit `DELETE` that **fires the FK action**, setting `task_id = NULL` on every session row. **Empirically reproduced** in this review: after the exact recreation sequence, `SELECT task_id FROM sessions` returns `null`. Triggers on every pre-V2 DB — precisely the population the migration exists to serve. The existing "preserves data" test omits a sessions table and the FK pragma, so CI can't see it.
**Fix:** wrap rebuilds in `PRAGMA foreign_keys = OFF` … recreate … `foreign_keys = ON` (the documented SQLite table-rebuild procedure); add `PRAGMA foreign_key_check`. Apply to all recreation blocks.

### CR-2 · Dead/contradictory CHECK-widening migrations that would cascade-delete logs if they ran
[`src/core/db.ts:51`](src/core/db.ts) and [`src/core/db.ts:182`](src/core/db.ts).

The probe `UPDATE sessions SET status='idle' WHERE status='idle'` can only throw if an `'idle'` row already exists — impossible on a legacy DB whose CHECK forbids `'idle'`. So legacy session tables are **never widened**, and the app throws `CHECK constraint failed` on the first `'idle'`/`'paused'` write. If the catch path ever did run it would: `DROP TABLE sessions` → cascade-delete `session_logs`/`session_messages` ([`db-schema.ts:85`](src/core/db-schema.ts),[`:93`](src/core/db-schema.ts)); copy only 14 of the columns (dropping `project_id`, `coding_agent_id`, …); and hit a guaranteed column-count error (`INSERT … SELECT *` of 18 cols into a 15-col table at [`db.ts:204`](src/core/db.ts)).
**Fix:** detect via `sqlite_master` SQL inspection (as `migrateTasksV2` already does), delete the dead tasks block, copy all columns, disable FKs during rebuild (CR-1).

### CR-3 · Watchdog kills slow/healthy turns and re-executes user messages — forever, no retry cap
[`src/core/process-manager.ts:556`](src/core/process-manager.ts) (`checkHealth`), [`:639`](src/core/process-manager.ts) (`requeueLastUserMessage`), [`:1071`](src/core/process-manager.ts) (`writeMessage`).

`writeMessage` sets `isProcessing = true` but never bumps `lastActivityAt`; only stdout handlers do. Any turn with >3 min of stdout silence (long build/test tool call, slow model) trips the watchdog: `SIGKILL` → `requeueLastUserMessage` `unshift`s the same message → respawn re-inserts it into `session_messages` and re-runs it. **No restart counter exists**, so a deterministically-slow turn is killed and re-executed every 3 minutes indefinitely — re-running an agent that may have already made partial worktree changes (duplicate side effects) and growing `session_messages` unboundedly. The watchdog also churns *idle* persistent sessions every 3 min.
**Fix:** bump `lastActivityAt` in `writeMessage` and the stderr handler; add a per-session restart counter (e.g. max 2, then fail the task); don't apply the threshold while `isProcessing` is false.

### CR-4 · Control-plane gate responses are silently lost for every plain-stdin agent
[`src/core/process-manager.ts:1095`](src/core/process-manager.ts) (`writeMessage`), [`:1255`](src/core/process-manager.ts) (`resolveGate`), [`:1295`](src/core/process-manager.ts) (`writeGateResponse`).

For plain-stdin agents (codex, gemini, opencode, cursor-agent, qwen, copilot), `writeMessage` closes stdin on send (`stdin.end(...)`). When the agent later emits `[DEVLOG_GATE]`, it's SIGSTOP-paused. On `resolveGate`, `writeGateResponse` hits the `writableEnded` guard and only logs "stdin no longer writable" — yet `resolveGate` **still clears the persisted gate** (`UPDATE sessions SET gate_status = NULL`, no rollback), sets `isProcessing = true`, SIGCONTs, and emits `gate_resolved` + `status: running`. The human's answer is permanently lost; the UI shows success. In the respawn branch it uses `stdin.write(... + "\n")` (never `end()`), so EOF-reading runners block forever.
**Fix:** clear `gate_status` only after a successful write; for plain-stdin runners route the answer through the normal send path (fresh process incl. prior context), or refuse `resolveGate` with an actionable error.

### CR-5 · Path traversal in worktree creation (`name` unsanitized → `git worktree add` anywhere on disk)
[`src/app/api/worktrees/route.ts:42`](src/app/api/worktrees/route.ts) → [`src/core/worktree-manager.ts:54`](src/core/worktree-manager.ts).

`POST /api/worktrees` reads `{ name, branch, baseBranch }` with only a falsy check, then `path.join(repoRoot, ".worktrees", name)`. `name = "../../../../tmp/pwn"` materializes a working tree (with repo files) at an attacker-chosen path. Reachable cross-origin from any webpage the user visits (no Origin check — see CR-6). `branch`/`baseBranch` starting with `-` are argument-injection into git.
**Fix:** validate `name` with `/^[A-Za-z0-9._-]{1,64}$/` and reject `..`; assert `path.relative(base, resolved)` doesn't escape; reject refs starting with `-`; pass `--` before positional paths.

### CR-6 · No Origin/Host/CSRF validation on any state-changing endpoint
Representative: [`tasks/[id]/execute`](src/app/api/tasks/[id]/execute/route.ts), [`tasks/[id]/pr`](src/app/api/tasks/[id]/pr/route.ts), [`tasks/[id]/retry`](src/app/api/tasks/[id]/retry/route.ts), [`worktrees`](src/app/api/worktrees/route.ts), [`sessions`](src/app/api/sessions/route.ts), [`projects/active`](src/app/api/projects/active/route.ts). No `src/middleware.ts`, no CORS/header config in [`next.config.ts`](next.config.ts).

Every mutating handler acts on body/params with no `Origin`/`Referer`/`Sec-Fetch-Site`/`Host` check. Under the stated threat model (a malicious local webpage, DNS-rebinding to `127.0.0.1`), every mutation is cross-origin reachable: create/execute tasks (spawn coding agents), delete tasks/sessions, **`git push` + `gh pr create` with the user's `gh` credentials** ([`tasks/[id]/pr`](src/app/api/tasks/[id]/pr/route.ts)), switch active project, and trigger CR-5 / CR-7. This is the single highest-leverage fix — it closes the remote trigger for most other issues.
**Fix:** add `middleware.ts` rejecting state-changing requests whose `Origin`/`Sec-Fetch-Site` isn't same-origin; validate `Host` against a `localhost`/`127.0.0.1:PORT` allowlist (defeats DNS rebinding).

### CR-7 · Unauthenticated endpoint spawns an arbitrary local binary via request-supplied `*_BIN`
[`src/app/api/agents/connection-test/route.ts:10`](src/app/api/agents/connection-test/route.ts) → [`session-runtime-auth.ts:302`](src/core/session-runtime-auth.ts) → [`process-manager.ts:329`](src/core/process-manager.ts) (`resolveConfiguredLocalCliBinary`) → [`agent-connection-test.ts:197`](src/core/agent-connection-test.ts) (`spawn`).

`local_cli_agent_env.{claude}.CLAUDE_BIN` (and `CODEX_BIN`/`GEMINI_BIN`/…) flow from the request body to `spawn(launch.command, …)` whenever `fs.existsSync(path)` is true. A malicious page POSTs `{"session_auth_mode":"local-cli","local_cli_agent_id":"claude","local_cli_agent_env":{"claude":{"CLAUDE_BIN":"/bin/sh"}}}` and DevLog launches it. Constrained to existing paths + agent-specific argv, but still arbitrary-existing-binary execution on an unauthenticated route.
**Fix:** only honor `*_BIN` overrides from persisted server-side settings (not transient request bodies), or restrict to an allowlisted directory; add the Origin check (CR-6).

### CR-8 · `devlog serve` is broken in the published binary, and the committed `dist` is stale
[`src/cli/commands/serve.ts:11`](src/cli/commands/serve.ts); packaging in [`package.json:7`](package.json).

tsup bundles to a single `dist/cli.js`, so `import.meta.dirname` is `<repo>/dist`; the three `..` in `path.resolve(import.meta.dirname, "..","..","..")` resolves *above the repo root*. **Empirically verified:** `node dist/cli.js serve` prints "Dashboard requires running from the DevLog source repo." and exits 1. Same bundled-layout bug makes [`setup-statusline.ts:120`](src/cli/commands/setup-statusline.ts) and [`setup-tmux.ts:144`](src/cli/commands/setup-tmux.ts) never find the shipped `scripts/`. Compounding it: the committed `dist/cli.js` is the npm `bin`, is weeks stale (still `VERSION = "0.4.0"` vs `package.json` `0.5.0`), `dist/` is even in `.gitignore` (force-added), and no `prepublishOnly`/`prepack` rebuilds it. Publishing today ships weeks-old code under a new version.
**Fix:** resolve the package root robustly (walk up to `package.json`); stop committing `dist/` and add `"prepublishOnly": "tsup"`, or add a CI step that rebuilds and diffs `dist/` against the commit.

### CR-9 · `scripts/generate-test-data.ts` deletes the user's real Claude Code history — and ships in the tarball
[`scripts/generate-test-data.ts:10`](scripts/generate-test-data.ts).

```ts
const CLAUDE_DIR = join(homedir(), ".claude", "projects");
try { rmSync(CLAUDE_DIR, { recursive: true, force: true }); } catch {}
```

`rm -rf ~/.claude/projects` (all real session logs, unrecoverable) at module load — no confirmation, no guard. `package.json` `files: ["dist","scripts"]` publishes it to npm.
**Fix:** target a dedicated fixtures/temp dir; require an explicit `--force`/env guard; remove `scripts/` (or just the harness files) from the published `files`.

## 🟡 Suggestions (high-value subset)

- **Dead code:** `active-sessions-panel.tsx`, `command-stats-bar.tsx`, `parallel-worktrees-panel.tsx`, `task-quick-view.tsx`, `devlog/stats-grid.tsx` are imported nowhere; `lock-manager.ts` is a fully-built API used only by its own test while [`file-watcher.ts:58`](src/core/file-watcher.ts) is the real (diverging) writer — and it inserts `file_locks` **without `project_id`**, so rows default to `'videoclaw'` and conflict queries return empty for every other project (a latent IM-level bug). Decide one owner; delete the other.
- **Schema DDL duplicated 4×** across `db.ts`/`db-schema.ts` and already drifted (root of CR-2). Single-source it.
- **Two persistence layers coexist** — `db.ts` cwd-singleton (`${cwd}/data/devlog.db`) vs `db-pool.ts` registry + per-project DBs — and `file-watcher`/`report-summary-store`/`task-lifecycle` still use the singleton, bypassing the multi-project model. Pick one; migrate callers.
- **`db.ts` registers SIGINT/SIGTERM → `process.exit(0)` at import** ([`db.ts:333`](src/core/db.ts)), hijacking the host's shutdown and masking non-zero exit codes. Move signal handling to explicit entrypoints.
- **Report date helpers duplicated** (`report-summary.ts` vs `report-evidence.ts`, already drifted 140 vs 160 char truncation). Extract `report-dates.ts`.
- **8 near-identical polling hooks** — extract one shared fetch/poll/stream utility with error state + sequence guard + singleton SSE (fixes IM-13/27/etc. structurally).
- **`recoverOrphanedSessions` uses `process.kill(pid,0)`** — recycled PIDs keep dead sessions "running"; also match start-time/command.
- **CI hardening:** actions pinned by mutable tags (`checkout@v4`, `setup-bun@v2`, `claude-code-action@v1` — the last holds an OAuth token + `pull-requests:write`). Pin to SHAs (dependabot will bump). *Positive:* the review workflow correctly uses `pull_request`, not `pull_request_target`.
- **Repo hygiene:** `tsconfig.tsbuildinfo` and machine-specific `devlog.config.json` (`/Users/moose/...` paths, personal `activeProject`) are committed; ship `*.example.json` + gitignore.
- **`engines.node: ">=18"` is false** — `commander@14`/`ora@9` need ≥20 and `import.meta.dirname` needs ≥20.11. Bump.

## Technology report for the development roadmap

Sequenced so each phase unblocks the next. Rationale in brackets.

### Phase 0 — Stop the bleeding (this branch, before any publish)
1. **Data-integrity migration fix (CR-1, CR-2).** Disable FKs during table rebuilds; replace UPDATE-probes with `sqlite_master` inspection; copy all columns; add `foreign_key_check`. *Ship-blocker: silent data loss on real user DBs.*
2. **Remove the destructive test-data script from the package + add a guard (CR-9).** *Ship-blocker: deletes user history.*
3. **Fix `serve`/packaging path resolution + stop committing stale `dist` (CR-8).** Add `prepublishOnly: tsup`; CI diff-check `dist` vs source. *The published binary is currently non-functional and stale.*

### Phase 1 — Security boundary (one focused PR, highest leverage)
4. **`middleware.ts`: same-origin + Host-allowlist guard (CR-6).** Closes the remote trigger for CR-5/CR-7 and IM-19/20/21 in one stroke.
5. **Input validation at boundaries:** worktree `name`/`branch` (CR-5/IM-22), `claude_session_id` (IM-19), task PATCH enums + project scoping (IM-20), local-CLI base-URL/`*_BIN` restriction (CR-7/IM-21).
6. **Generic error responses** (stop echoing raw git/fs/python messages) once routes become cross-origin-readable.

### Phase 2 — Runtime correctness & lifecycle
7. **Process-manager hardening (CR-3, CR-4, IM-5/6/9):** activity bump in `writeMessage` + restart cap; gate delivery that doesn't lie about success; persist `exit_code`; identity-checked `close` handler; release linked tasks on orphan recovery (IM-8).
8. **Single owner for process & file-lock lifecycle** — delete `lock-manager` *or* `file-watcher`'s inline path; fix the `project_id` default bug.
9. **Dedicated instance-level ProcessManager tests** with a fake `ChildProcess` (spawn→close→respawn races, watchdog requeue, kill/SIGKILL fallback, pause/resume, gate delivery). *This is the largest untested risk surface.*

### Phase 3 — Correctness of the numbers (the product's whole point)
10. **One timezone end-to-end (IM-3)** + per-message cost/duration attribution (IM-1, IM-24). Add TZ-boundary tests (CI already pins `TZ=Asia/Shanghai` — make it meaningful).
11. **Parser coverage** for legacy/string-content events (IM-2) and `firstActivity` (IM-4); first tests for `discovery`/`parser.parseSessionFile`/`vcc`/`paths`.

### Phase 4 — Performance & scale (as history grows)
12. **Incremental discovery cache (IM-23)** keyed by `(path,mtime,size)` with bounded concurrency — single biggest UX win for large histories; also fixes CLI cold-start (IM-29).
13. **Shared frontend data layer (IM-13/27/28/30):** one fetch/poll/stream utility (error state + sequence guard + singleton SSE), memoized chat rendering, optimistic kanban.
14. **Bound the unbounded:** VCC cache (IM-25), db-pool handles (IM-26), provider chat history, per-turn text/tool-use buffers.

### Cross-cutting / architecture decisions to settle now
- **Consolidate the two persistence layers** (cwd-singleton vs per-project pool) before building more on either — every new feature currently has to pick one and risks divergence.
- **Move process-lifecycle/signal ownership out of the data layer** into explicit entrypoints.
- **Adopt a validation library at API boundaries** (e.g. `zod`) so route bodies are parsed, not trusted — this is the structural fix that makes Phase 1 durable rather than whack-a-mole.
- **Establish `dist`-freshness and TZ-correctness as CI gates** so the two classes of "green CI, broken artifact" bugs found here can't recur.
